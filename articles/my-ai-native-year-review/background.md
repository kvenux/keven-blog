# 我的AI Native周年记

## 从Gemini 和 Andrej Karpathy说起


从去年5月份开始大规模使用Gemini 2.5 pro以来，我的开发、思考有了很大的变化，正好也是做AI Coding方向的，把这一年流水账记录一下，算是打个结。

回头看过去这一年，我觉得很难把变化归结到某一件具体的事情上。它更像是几个阶段，以及几个比较重要的时间点。每一个阶段，我使用 AI 的方式、对 AI 的理解，以及我对自己的认识，都发生了一些变化。

一开始，这种变化主要发生在工作方法上。后来，它逐渐进入我的生活、思考习惯、自我反省和理解他人。再后来，我开始重新理解自己为什么能在 AI Native 这件事情上跑得比较快，也重新理解了我过去读博、做研究、做编译器大作业以及长期“折腾”的经历。

到最后，这不再只是“我学会了使用几个 AI 工具”，而是我对学习、创造、管理、人与人之间的协作，甚至对模型和 Agent 行业本身，都形成了一套新的看法。

---

## 二、2025 年五一前后：Gemini 2.5 带来的第一个转折点

2025 年五一前后，Gemini 2.5 出来了。

当时我对这个模型最直接的感受就是：它非常 powerful，能力很强。与此同时，Google 当时给的免费额度非常多，甚至可以说是超级多。Google AI Studio 有一个偏实验性质的网站，基本上可以依靠免费额度大量使用。

因此，那段时间我不只是拿它来写代码或者处理工作。我平时工作中遇到的问题、生活中遇到的问题，以及我自己产生的一些想法，都会拿去和它讨论。

我会不断地思考、不断地问。渐渐地，它变成了我的一个很重要的助手。这个助手不只存在于工作环节，而是开始进入我的日常思考过程。

这应该算是我从“偶尔使用大模型”，转向“把大模型当作日常认知工具”的一个重要转折点。

---

## 三、Karpathy 的一条推文，以及“手拼上下文”的时代

差不多在同一时期，还有一个对我影响很大的转折点，就是我看到 Karpathy 的一条推文。

我对那条推文的理解大概是：现在做 Coding，可以写一个脚本，把项目的所有相关上下文打包起来，连同你的要求一起发给 AI，让 AI 基于这些完整的上下文来工作。

我按照这个套路去实践之后，获益非常大。

### 1. 我写了一个提取项目上下文的脚本

我自己写过一个脚本，用来把某个文件夹中的内容提取出来。

当时的实际情况是，我脑子里对项目有一个大概的认知。我知道每个模块大概是干什么的，也知道一个需求可能需要修改哪个模块。但是，我不会事先把那个模块里的所有具体代码都翻出来，逐行阅读一遍。

我的做法是：

当我拿到一个需求，判断这个需求应该改某个模块之后，我就把需求写在最前面。然后把与这个模块相关的目录、文件夹，以及里面所有相关文件，通过脚本封装起来，再通过 API 的形式发给大模型。

最开始，我主要是把代码和上下文封装成纯文本。后来，我也尝试把 AST 一类的信息转换成可以通过 API 提交的形式。整个过程主要依靠纯脚本完成。

### 2. 我和大模型一起建立对项目的认知

那时候开发一个项目，大概是这样的过程：

我先拿到需求，然后把和需求相关的项目上下文拼起来，一次性发给大模型。

刚开始的几轮，我通常不会马上要求它给最终代码，而是先和它讨论：

这个需求应该怎么修改？

可能涉及哪些模块？

有哪些设计决策？

不同方案之间有什么取舍？

它返回之后，我会自己消化、理解，再把更加详细的修改方式写进新的用户提示词里。

所以，那时的状态其实不是简单的代码补全。它更像是我和大模型一起，对这个项目建立认知。在讨论过程中，我们共同把模糊的需求变成明确的设计决策，再变成具体的修改方案。

这和后来 Agentic Coding 自动定位上下文的方式不一样。那时候，项目上下文是我手动选定的。

我知道需求涉及哪个模块，所以我决定把哪些目录、哪些文件发给模型。模型不负责在整个项目里自主搜索，它是在我圈定的范围内工作。

### 3. 模型负责建议，我负责真正修改

当时我还会要求大模型把需要修改的代码用 highlight 或者代码框标出来。

它给我的主要是一份 Markdown 格式的输入输出。我会在这份 Markdown 结果上继续工作，再手动把它提出的修改落实到项目代码里。

也就是说，整个修改过程还是由我亲手完成的。

在这个过程中，我会知道这次改动涉及哪些文件，也会大概审查它生成的代码。哪怕不是逐字符审查，我至少会理解改动发生在哪里、为什么要这样改，以及它有没有满足我的要求。

这种深度参与感，对我来说非常有用。

### 4. Git 回退让试错成本变得非常低

这一套流程通常发生在 Git 项目中。

每完成一轮改动，我都会判断结果是不是合适。假如这一轮效果不好，或者方向不对，我就直接 discard，把这一轮改动全部回退掉。

因此，虽然那时没有完整的 Agent，也没有现在这种自动搜索、自动修改、自动运行测试的闭环，但是生产效率已经很高了。

我可以非常快地尝试一个方向。合适就保留，不合适就直接回退，不需要为已经投入的代码产生太多心理负担。

## 四、手拼上下文与 Agent 自动定位：效率和学习并不是同一件事

后来 Agentic Coding 逐渐成熟，Agent 可以自动搜索代码、自动定位上下文、自动修改文件，还可以把验证过程集成进去。

这种自动化确实降低了门槛，也在一定程度上提升了效率。

但是，从人的学习效果来看，我觉得它未必比手拼上下文更好。

手拼上下文的时候，我必须自己判断：

这个需求和哪个模块有关？

哪些目录需要发给模型？

模型返回的修改应该落在哪些文件里？

它的代码是否符合我对项目的理解？

我还要亲手把修改应用到代码里。

因此，我在整个过程中会逐渐形成对项目结构的理解。模型虽然帮我做了很多思考，但我并没有从项目中退出。我仍然处于整个开发闭环之内。

而自动化 Agent 的问题在于，它把上下文定位、文件修改甚至验证都包办了。效率提高了，但人也可能因此失去对项目细节的参与。

所以我现在会觉得：

自动定位上下文降低了使用门槛，也让执行更高效；但从人的学习、理解和能力积累来看，手拼上下文的时代可能反而更有价值。

---

## 五、从两天到一两个小时：AI 对个人创造效率的放大

我平时周末很喜欢自己“整活”。

在读博的时候，我一到周末也经常会做一些自己的事情。有时候研究暂时做不下去了，我也会转去做一些工程上的尝试。

但是以前受限于人脑算力，一个想法从出现到真正做出来，往往需要很长时间。

例如，我以前做过一个蚂蚁森林自动收能量的脚本。

这个项目需要通过图片识别找到能量泡，然后再和手机侧的自动化测试能力结合起来。它有点像 Selenium，只不过操作对象是手机。我要把截图、图像识别、坐标定位和手机操作整个串起来。

这样一套东西，以前哪怕做得再快，最快也要两天左右才能搞定。

进入手拼上下文的阶段之后，类似的事情可能一两个小时就能做出来。

原因是很多底层知识 AI 本身已经知道了。它知道 Selenium 或类似自动化工具应该怎么连接，知道截图应该怎么做，也知道这些模块大致应该如何串联。

我需要做的主要是把任务拆清楚。

当然，这里有一个很重要的前提：我自己也懂这个任务。

我知道它有哪些组成部分，知道各部分之间应该如何协作，也知道最后做出来的东西是否正确。因此，虽然 AI 大幅加快了执行，我仍然在全程掌控项目。

---

## 六、我越来越意识到：我首先是一个 Builder

在这段时间里，我越来越清楚地意识到，我是一个 Builder。

我身上“程序员”的那一面，可能没有想象中那么重要。真正更强的部分，是我对所做事情本身的方向判断。

我擅长判断：

这个东西值不值得做？

应该往哪个方向做？

哪些设计是关键的？

AI 给我做出来的东西能不能验收？

它到底有没有解决真正的问题？

所以，AI 并没有简单地替代我的编程能力。相反，它让我更清楚地看见，我的核心价值可能本来就不在于一行一行地写代码，而在于定义问题、判断方向，以及验收结果。

---

## 七、AI 进入了我的日常思考：第一性原理与“中立的思考辅助器”

那时我不只是在写代码的时候使用 AI。

因为每天都在和 AI 一起工作，所以平时产生的一些思考，我也会和 AI 一起讨论。例如，我会和它探讨一个方向的本质，或者反复分析一个问题为什么会发展成现在这个样子。

我最常说的一句话就是：

“用第一性原理分析。”

我当时觉得，AI 是一个相对中立的思考辅助器。

和一个有情绪的人交流时，很多时候你不仅要处理问题本身，还要处理对方的情绪、立场、身份和防御。AI 至少在表面上更容易把讨论维持在问题本身。

当然，和 AI 对话最大的挑战仍然是：你必须自己判断它给你的信息。

它可以给出看起来非常完整、非常有逻辑的回答，但最终你需要判断这些东西到底对不对、适不适合当前场景。

因此，AI 不只是一个答案生成器。它更像一个可以高速陪我推演问题的对象，但判断权仍然必须掌握在我自己手里。

---

## 八、生产力暴涨之后，我进入过一种“赛博精神病”状态

在个人生产力突然提升之后，我觉得自己一度进入了一种有点像“赛博精神病”的状态。

因为我一个人的生产力上来了，我对 AI 的要求也提高了，所以我很自然地把类似的要求放到了周围同事身上。

但很多同事当时并没有大规模地使用 AI。

他们没有进入和我一样的工作节奏，也没有经历同样的信息密度和效率提升。在这种情况下，我却用自己经过 AI 放大之后的节奏去要求他们，其实对他们是不公平的。

我也产生过自我怀疑。

我有时会觉得自己太急躁了，说话也特别直接。

### 1. 和人打交道非常耗费token

我后来意识到，跟人打交道是一件很耗费token的事情。

你需要管理对方的预期。

你必须根据对方的理解能力，选择和他认知水平相匹配的描述方式。

你要把事情讲明白，还要照顾他的情绪。

因为人是有情绪的动物。很多时候，情绪甚至会占主导。人不一定一直处在纯理性状态，也不一定能时时刻刻意识到双方只是在就事论事。

我自己有时甚至不太关注自己的情绪，但我不可能要求所有人都和我一样。

和 AI 沟通的时候，可能一句话就能把事情讲明白；和人沟通时，同一件事往往需要花很多口舌。

于是，我会明显感觉到沟通效率变低了。

### 2. 我开始厌恶会议，也越来越不适应听人说话

那段时间，我比较厌恶会议。

会议里大家七嘴八舌，交流常常显得不够高效。很多人说了很久，却没有形成一个明确的问题定义、结论或者下一步行动。

与此同时，我因为长期和 AI 交流，越来越习惯于这样一种模式：

我打字，把完整的想法输出给 AI；AI 返回一段文字，我快速阅读。

我的阅读速度比较快，思考速度也比较快。

但是听人说话时，对方的输出速度本身就比较慢。我必须强行让自己的思考速度和对方说话的速度匹配。

在匹配的过程中，我还要不断判断他的认知背景，理解他真正想表达什么，再把他的表达映射到我自己的问题框架里。

整个过程让我觉得非常累。

大约从 2025 年五月到下半年，甚至一直到十月、十一月，我都处在这种状态里：一方面生产效率非常高，另一方面越来越不适应传统的人际沟通节奏。

---

## 九、通过使用模型，我真正理解了大模型，而不是只“知道原理”

从 2025 年五月到十一月左右，我基本上是靠这套“手拼上下文”的脚本走天下。

在这个过程中，我对大模型接口本身也进行了非常深的实践。

包括：

Token 的输入和输出；

模型推理中的 prefill 和 decode；

上下文如何影响模型表现；

为什么模型有时 follow 指令、有时不 follow；

为什么你和它说了某件事，它有时像是听懂了，有时又像没听懂；

模型有哪些固定弱点；

Agentic 工作流是怎么运作的；

Tool Call 的过程和边界是什么。

这些东西，我以前可能也看过原理，甚至能够把原理讲给别人听。但我越来越发现，一个人对知识的掌握，并不是“看到了原理、能够复述”就够了。

真正的理解，是在每天的使用和实践中逐渐变深的。

它会嵌入各种奇怪的 Debug 场景，嵌入失败案例，嵌入模型不听话的时候，也嵌入每一次你重新修改提示词、重新组织上下文和重新设计工具调用的过程中。

所以我现在越来越相信实践。

甚至可以说，要知行合一。

很多时候不是先完全“知”，再去“行”，而是你先行动，才会逐渐知道。

仅仅觉得自己知道了更多，却没有真正做过，这种“知道”可能是有问题的。只有遇到问题之后真正行动，你对整个问题的认知才会发生明显提升。

## 十、2025 年十月至十一月：Claude Code 与 Opus 4.5 的转折

大约从 2025 年十月开始，我开始使用 Claude Code。

十一月左右，Opus 4.5 的发布又成为一个比较标志性的事件。

在这之前，我其实没有特别关注 Anthropic。虽然我知道 Sonnet 写代码很强，但在更早的二月份，我曾经用过一次，当时感觉很“水”。我也充过钱，但后来基本没再用。

那时我主要使用 OpenRouter，因为它上面可以调用很多家的大模型，方便我比较不同模型。

但是后来真正使用 Opus 4.5 之后，我发现它的能力非常强。

我甚至听到有人用“像是由一个哲学家训练出来的”来形容它。对我来说，它的特别之处不只是某项 Benchmark，而是一种整体上的世界建构能力、联想能力，以及它表达出来的 sense。

我可以直接用自己熟悉的语言和它对话，而它输出的东西，会让我明显感觉到更像人在写。

因此，我开始使用 Opus 4.5 写文章。

整体上，我觉得它是一个非常“高级”的模型，是一种高级货。

### Claude Code 把上下文定位这件事做顺了

差不多同一时期，Claude Code 也迎来了一次明显的爆发。

从 2025 年年底开始，我基本上大量使用 Claude Code 来做开发。

过去我们为了解决项目上下文问题，会尝试先总结大量文档，例如：

整个模块的功能设计是什么；

各个文件夹分别承担什么职责；

模块之间是什么关系；

哪些关键文件对应哪些能力。

我们希望先建立一张项目地图，再根据地图寻找相关代码。

这种思路直觉上是合理的，但它依然需要人提前进行大量整理。

Claude Code 做得比较好的一件事情，是它可以利用 Bash、命令行搜索和项目内检索，自主地追踪上下文、寻找关键文件。很多过去必须由我手动完成的上下文定位活动，可以直接交给 Claude Code。

因此，大约从十月开始，我的工作方式开始从“手动圈定上下文”，向“让 Agent 自己寻找上下文”转变。

---

## 十一、2026 年一月：OpenCode 火爆，以及我走过的两类弯路

到了 2026 年一月，OpenCode 短暂地火了起来。它在 GitHub 社区里的热度也比较高。

我当时深入分析了 OpenCode 的原理，也实际用它做了一些事情。

不过，那段时间我走过一些弯路。

### 第一类弯路：中转站

中转站的一个吸引力是，不用自己解决翻墙或者官方访问的问题，接入比较方便。

但我后来越来越觉得，中转站很不安全，也有非常大的操作和套利空间。

各家模型厂商的官方订阅套餐，通常会有五小时窗口、周窗口等限制。但从实际成本来看，订阅套餐远远便宜于 API。

按照我自己做实验和测量得到的结果，API 的等价价格可能是订阅套餐的五十到一百倍。

中转站实际上利用了这个价格差。

它可能按照接近 API 的价格和用户结算，但背后使用的并不是同等价格的官方 API，而是用大量订阅账号组成一个池，再把这些订阅额度转供给用户。

这里存在很多问题。

首先，你不知道它实际调用的到底是哪一个模型。

有些中转站会出现明显的“降智”，即使它声称提供的是某个模型，你也无法确定背后是不是真正的那个模型，或者是不是做了替换、路由和降级。

其次，服务稳定性很差。

我当时用过很多中转站，整体感觉都不太靠谱。

同样一个模型，通过中转站干活，往往又慢，效果又不好；而通过官方订阅使用，体验明显更好。

我甚至会怀疑，中转站背后到底有没有真的在调用它所宣称的模型。

因此，后来我基本上不用中转站了。

### 第二类弯路：复杂插件和巨量 Token 工作流

第二类弯路，是 OpenCode 上的一些复杂插件，例如 Oh My OpenCode。

它在 OpenCode 的基础上增加了很多复杂能力，但同时也大幅增加了 Token 消耗。

里面有 Ultra Work 一类的模式，也有一整套以希腊神话人物命名的 Agent、角色和工作流。

那段时间，为了使用 Oh My OpenCode，我甚至记住了很多希腊神话人物的名字。

但后来回头看，我觉得这其实没有太大必要。

这些复杂工作流的本质，往往是通过非常大的 Token 量和非常大的工作量，让模型反复思考、反复推理，试图进一步压榨模型的能力。

它确实很耗 Token，但是最终带来的实际提升并没有那么大。

所以在 Oh My OpenCode 这件事情上，我也走过不少弯路。

## 十二、Vibe Coding 像游戏一样，让我停不下来

那段时间，我在周末会非常希望自己能一直和 Vibe Coding 待在一起。

因为创造带来的多巴胺奖励实在太强了。

你产生一个想法，把它告诉模型，模型迅速开始执行。很短时间内，一个原本只存在于脑子里的东西，就能够运行起来并给你反馈。

这种即时反馈很像游戏。

### 1. 周末、家庭和“偷偷 Coding”

平时工作已经很忙，所以我非常珍惜周末可以使用 Claude Code 和各种外部大模型的时间。

一到周末，我就会一直坐在电脑前。

但是家里人，尤其是我老婆，会希望我陪一陪孩子。

于是我的状态就很像以前玩游戏：

表面上在带娃，实际上总想找机会偷偷 Vibe Coding 一会儿。

但站在我老婆的角度，她肯定会觉得我没有真正好好带孩子。所以那段时间，我的家庭地位也会比较低。

我老婆当时并不太理解人工智能革命对每个人到底意味着什么。

但另一方面，我自己当时也确实处于一种比较浮躁、比较上头的状态。

不能简单地把问题归结为她不理解 AI。我自己也没有处理好创造冲动、工作节奏和家庭责任之间的关系。

### 2. 去泰国度假，我也要把“干活摊子”支起来

这种状态夸张到什么地步？

我去泰国玩，到了酒店之后，第一件事之一就是把电脑打开，把干活的摊子支起来，把各种 Session 都打开，然后让它们开始干活。

我明明是去度假的，但整个状态看起来还是像在打工。

我还去过泰国那种数字游民的共享办公空间，在那里干了一个下午的活。

当时我反而觉得很清爽。

因为创造的结果会很快得到反馈，这种高速反馈会带来非常强的满足感。

### 3. 睡觉之前绝对不能打开

我在那段时间深刻理解到，Vibe Coding 和玩游戏真的很像。

它会让人停不下来。

尤其是晚上睡觉之前，绝对不能打开。

一旦打开，你基本上就会失眠。因为你会不断地产生新想法，不断想看 Agent 运行到哪里了，不断想再修改一点、再试一个方向。

这和以前睡前玩游戏的感觉非常像。

## 十三、后来我开始意识到：快不一定是一件好事

现在，我的状态已经有所转变。

我开始觉得，快不一定永远是一件好事情。

有时候我甚至会怀疑，自己到底能不能真正驾驭 AI。

当然，这个问题也不能简单地归结为“能”或者“不能”。它更像是我开始重新审视：高速生成、高速执行、高速反馈，是否真的等于成长和掌控。

我本质上仍然更喜欢一些底层的东西，更喜欢通过较长时间的实践，把一个问题真正搞明白。

这种偏好和我过去的经历有关。

## 十四、编译器大作业：我为什么相信实验、动手和带着问题学习

我大学期间做过编译器。

那个项目要求用 C 语言实现一个 C 语言编译器。

老师当时给的指引很少。因为它本身是一个比较新的课题，能够直接参考的现成材料也有限。

一开始，从词法分析、语法分析入手，通过嵌套的文法分析，把源代码解析成四元式。这部分虽然复杂，但大致路径是可以理解的。

真正困难的是从四元式生成汇编语言。

你必须很懂汇编，才能把这件事情做出来。

正好我当时对汇编语言比较熟，所以我能够把从中间表示到汇编生成这一步搞定。

但是更大的问题，是优化。

编译器最后做得好不好，很多时候输赢就发生在优化上。

例如：

怎样分配寄存器；

怎样减少访存；

怎样降低内存访问指令的数量；

怎样让生成的汇编更紧凑；

怎样在有限寄存器的条件下安排变量和中间结果。

这里有大量具体的小 trick。

这些 trick，老师平时不一定会教，书上也不一定能够直接查到。

所以我当时动用了各种资源去找。

后来，我们老师也很给力，专门找了一位来自英特尔、做编译器的专家，给我们讲了一节课。

那一节课，是我大学期间听过的信息密度最高的一节课。

原因不只是专家讲得好，更重要的是，在听这节课之前，我已经做过很多编译器优化方面的尝试。

我是带着问题去听的，也带着非常强的实践经验去听。

所以他讲到一些点的时候，我会觉得一下子被击穿了，很多过去模糊的问题突然恍然大悟。

后来，我还专门去找那位编译器专家请教。

最终，在那个大作业里，我几乎把能想到、能找到的优化手段都用上了。在相关优化指标上，我做到了相当高的水平，部分评测或者优化表现达到了百分之八十以上。最后那门课我也拿了九十多分。

它说到底只是一个几个学分的大作业。

但我觉得，它对我的整体学习方式，甚至对我后来研究型人格的塑造，都产生了非常大的影响。

它让我更习惯于相信实验，相信亲手去做。

我会用动手来驱动自己建立认知。

## 十五、我为什么能在 Vibe Coding 时代比别人跑得快

我后来也逐渐理解，为什么自己在 Vibe Coding 的过程中会比很多人跑得快。

首先，我确实是一个“行胜于言”的人。

我更习惯先做起来。

其次，我是被好奇心驱动的。

很多事情并不是因为有人要求我做，也不是因为做完之后能立刻得到明确收益，而是我真的想知道它能不能成立、底层到底是什么、继续往前走会发生什么。

更重要的一点是，我不怕犯错，也不怕受挫。

我有比较强的韧性。

我做事情一直有一个风格，叫作：

“先把孩子生出来。”

也就是先把第一版搞出来。

只要第一版出现了，你就可以开始迭代。

这第一版可能直接崩掉，也可能上线之后得到一片骂声。但这些事情我并不是特别 care。

因为我对自己的判断，并不建立在名声、荣誉或者某个领导的夸奖之上。

我不会因为别人暂时不认可，就完全否定一个方向；也不会因为别人夸了几句，就认为这件事情一定是对的。

我对自己在做什么，通常有一个相对清醒的认识。

所以，我的风格并不是在所有信息都完备之后才开始，而是先把东西做出来，再通过真实反馈不断迭代。

## 十六、2025 年以前，我后悔读博；2025 年以后，我不再后悔

在 2025 年以前，我其实很后悔自己读博这件事情。

读博期间，我过得挺艰难。

基本上很多时候是自己指导自己，也有很长时间发不出一篇文章。那段经历让我陷入过非常深的自我怀疑。

与此同时，读博有很大的机会成本。

当时正好是资产价格快速变化、很多同龄人开始积累财富的阶段。和同龄人相比，我可能因为读博错过了一些挣钱和买房的机会。

粗略地说，可能至少相当于少买了一套房。

所以在很长时间里，我对读博是有些后悔的。

但是到了 2025 年以后，我不太后悔这件事情了。

因为我逐渐发现，读博实际上给了我一个很好的 gap。

它让我暂时从那种以挣钱为中心、非常激进的思维定式里逃脱出来。

在那段时间里，我被迫真正和自己相处，也逐渐发掘出了自己的内驱力。

我发现，自己真正愿意长期做事情的动力，来自好奇心。

这件事在 AI Native 的探索里尤其重要。

因为当你面对一个大模型对话框，或者面对一个 Coding Agent 的窗口时，没有人天然告诉你应该做什么。

假如你没有好奇心，也没有自驱力，你甚至不知道应该在那个窗口里输入什么，不知道要让它帮你探索什么，更不知道自己究竟想创造什么。

所以对我个人来说，读博最终是一件很好的事情。

当然，我不会去感激苦难本身。

但是我会感激那个在苦难里不断挣扎、不断折腾、不断找出路的自己。

## 十七、2026 年春节前后：从 Claude 一侧转向 ChatGPT 和 Codex

这段过程大致延续到了 2026 年年初，包括春节之后。

后来，在我的感受里，Claude 一侧的产品政策越来越政治化，也越来越极端化。与此同时，它的 4.7、4.8 等版本，在我的实际使用中写代码的表现比较拉垮。

于是，我后来又转向了 ChatGPT。

现在一些比较深度的思考，我基本上会放到 ChatGPT 上完成。

一方面，它的成本相对合适；另一方面，网页版 Pro 里的 GPT 5.5 Pro，整体思考能力非常强。

因此，我会把很多分析、推演和深度思考放在 ChatGPT 里。

主要的开发和作业工具，则又切回到了 Codex 这一侧。

---

## 十八、从手拼提示词到 Agent：人的工作从“写代码”转向“前置定义”

有了完整的 Coding Agent 之后，工作方式和过去手拼提示词的状态很不一样。

过去，我是在 Coding 的过程中逐渐思考。

我可以一边改代码，一边发现需求还有哪些地方没想清楚，再回头调整设计。

但是现在，当我让 Agent 自己干活时，我必须在它开始工作之前，花很大精力想清楚：

这个软件到底应该被定义成什么样子？

我要交给它的任务是什么？

有哪些明确要求？

哪些边界不能突破？

什么结果才算成功？

因为 Agent 一旦跑偏，它往往会越跑越偏。

方向性的错误，后期修复的代价非常高。很多时候，你需要加倍偿还早期没有想清楚的东西。

因此，在 Agent 开始干活之前，必须仔细思考给它的输入是否得当。

这是从“边写边想”，转向“先定义，再执行”。

人的价值也因此越来越集中在前置思考和方向判断上。

---

## 十九、自我验证闭环，是 Agent 真正产生杠杆的关键

我现在会非常重视让 Agent 建立一个自我验证闭环。

因为只要它可以自己验收自己的活，很多事情就能事半功倍。

例如，写一个 Web 应用时，你需要理解 Playwright 应该怎么使用，然后让 Agent 通过多模态能力或者浏览器交互，自己验证页面是否符合要求。

它不能只写完代码就宣布完成。

它应该能够启动应用、打开页面、执行操作、观察结果，再判断自己的实现是否真的满足需求。

假如写的是 CLI，那么 CLI 的输出最好尽量 JSON 化，或者至少是对模型友好的结构化输出。

这样 Agent 才能方便地读取结果、比较预期，并判断任务有没有成功。

所以你不仅要告诉 Agent 做什么，还要告诉它：

什么叫作“做得好”；

什么结果算通过；

应该使用什么方法进行验收。

从这个角度看，我现在做的事情，本质上越来越像管理。

就像你在带一个实习生：

你要告诉他任务怎么拆；

拆完之后，每个任务应该怎么做；

做完之后，又应该怎么验收。

这已经不是简单地把编码工作交给模型，而是在设计一个可以自主执行、自主验证的工作系统。

---

## 二十、后训练越来越强：Agent 只是模型能力外化的一层脚手架

随着大模型后训练能力越来越强，我对 Agent 的理解也发生了变化。

2026 年三月左右，Claude Code 出现源码泄露一类的事件。我当时对相关内容进行了比较深入的分析。

我发现一件让我觉得很“可怕”的事情：

它背后的模型后训练、Agent 提示词增强，以及大量深度人工参与的机制，很可能不是几个孤立模块，而是整个数据和训练体系串在一起的。

Claude Code 自己产生的大量过程数据和轨迹数据，可以继续反过来用于模型后训练。

也就是说，Agent 在真实任务中的完整行为轨迹，包括它如何搜索文件、如何理解项目、如何修改代码、如何调用工具、如何验证结果，都可能成为后续训练的高价值数据。

### 1. 源码泄露后，最大受益者可能不是 Agent 厂商

我一直有一个观点：

Agent 是模型能力外化的体现。

它只是模型外面一层相对薄的脚手架，核心仍然是模型。

而且，一个真正强的 Agent，一定要和模型进行深度耦合。

因此，在我的判断里，Claude Code 源码或内部机制泄露之后，获益最多的可能不是那些单纯做 Agent 外壳的厂商，而是各大模型训练厂商。

因为他们相当于免费获得了一个专家轨迹生成器。

他们可以使用 Claude Code 一类成熟工作流，生成大量高质量的 Agentic Coding 轨迹，再用这些轨迹去做模型后训练。

这也能解释为什么 GLM、MiniMax 等模型的新版本一出来，就能和 Claude Code 一类工具适配得比较好。

我的推测是，它们很可能已经在使用类似 Claude Code 的环境和工作流生成轨迹数据，再针对这些轨迹进行训练。

从这个角度看，Claude Code 可能是这个行业里较早真正把 Agentic Coding 玩明白的产品之一。

它不只是做出了一个工具，还在事实上定义了一套标准。后来很多模型厂商，都开始按照这套标准准备后训练数据、优化工具调用方式和工程能力。

---

## 二十一、模型能力正在“吃掉”Agent Harness 的空间

我感觉现在模型的后训练已经强到了一种比较夸张的程度。

例如，在我的实际体验中，GPT 5.6 的后训练能力非常强。

它可能只需要使用非常简单的 `rg`、文件检索或命令行搜索，就能够把一个项目理解得非常透彻。

而我过去一直在做一些帮助模型理解项目的工具。

这些工具在旧模型上可能很有效，因为旧模型不擅长自己定位上下文，也不擅长从大量代码中建立稳定认知。

但是新模型一上来，模型自身能力直接把这部分空间吃掉了。

原来需要额外 Harness 才能完成的事情，现在模型依靠很简单的搜索和推理就可以完成。

所以，我有时也会觉得挺受伤的。

我们这些做 Agent Harness、做模型外部脚手架的人，很多工作可能面临一个瓶颈：

假如我们不能沿着模型本身的能力演进方向去做，也无法参与模型后训练，就很难做出真正突破性、革命性的成果。

模型外部的工程当然仍然重要，但很多核心能力最终还是会被吸收到模型和后训练过程中。

因此，Agent 必须和模型后训练结合。

仅仅在模型外面加越来越复杂的 Harness、插件、角色和提示词，未必能够长期建立壁垒。

模型训练，尤其是模型后训练，依然是非常重要的核心环节。

---

## 二十二、这一年真正发生的变化

回头看这一年，我经历的并不只是工具切换：

从 Gemini 2.5 到 Opus 4.5；

从 OpenRouter 到官方订阅；

从手拼上下文到 Claude Code；

从 OpenCode 和 Oh My OpenCode 的复杂工作流，再回到更直接的工具；

从 Claude 一侧转向 ChatGPT 和 Codex。

真正的变化，是我和 AI 的关系发生了变化。

最开始，AI 是一个能力很强的助手。

然后，它变成一个可以和我共同建立项目认知的协作者。

再后来，它开始自主寻找上下文、自主修改代码、自主调用工具。

到现在，我越来越像是在管理一个可以执行任务的智能体：我需要定义问题、约束方向、拆解任务，并设计验证闭环。

与此同时，我也经历了 AI 对个人生活的反噬：

因为生产力提升而对同事产生不公平的要求；

因为习惯了高速文字交互而越来越难忍受低速会议；

因为创造反馈过于强烈而像沉迷游戏一样沉迷 Vibe Coding；

因为周末一直坐在电脑前而影响家庭关系；

甚至在泰国度假时，也忍不住打开电脑、支起所有 Session 继续干活。

最终，我开始意识到，效率并不是唯一目标。

快也不一定永远是好事。

真正重要的，是我是否仍然理解自己在做什么，是否保留了判断力，是否能驾驭这种被 AI 放大的创造能力，以及是否能把这种能力放进一个可持续的工作和生活结构里。

而我之所以能够比较快地进入 AI Native 状态，并不只是因为我比较早地用了某个模型。

更深层的原因，是我过去形成了一套行为模式：

相信实验；

相信动手；

用实践驱动认知；

用好奇心驱动探索；

不害怕失败和回退；

先把第一版做出来，再持续迭代；

不把判断建立在名声、荣誉和外界评价上；

在受挫之后仍然愿意继续折腾。

这些东西，来自我过去做编译器的经历，也来自读博期间长期独自摸索的经历。

我不会感激那些苦难本身，但我会感激那个在里面挣扎、行动，并最终形成自己内驱力的我。

接下来，我可能还会进一步补充两部分内容：一部分是我对“认知四象限”的理解，另一部分是人在 Agent 时代究竟应该如何与 AI 工作。现在这份内容，则可以作为整篇 AI Native 周年记最完整的一版素材母稿。
