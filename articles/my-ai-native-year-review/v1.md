# 我的 AI Native 周年记：从效能倍增到重新认识自己

去年去泰国旅行时，我专门找了一家数字游民共享办公空间，在那里干了一个下午的活。

照片里的我坐在电脑前，把不同的 Session 打开，让 Agent 同时跑起来。当时的感觉非常好：一个想法刚刚冒出来，没过多久就能变成一个可以运行的东西。创造带来的反馈如此迅速，以至于那天下午坐在电脑前，反而让我觉得很清爽。

<!-- 泰国数字游民共享办公空间照片放在这里 -->

现在回头看，这张照片很能代表我的 AI Native 第一年。

AI 明明替我节省了大量时间，我却把所有节省出来的时间，又重新交给了 AI。以前两天才能完成的东西，后来一两个小时就能做出来；但我并没有因此获得更多空闲，反而越来越停不下来。

这一年，我表面上经历的是一连串模型和工具的切换：从 Gemini 2.5 Pro，到 Opus 4.5 和 Claude Code，再到 GPT-5.5、ChatGPT 和 Codex；从手工拼接上下文，到 Agent 自己搜索代码、修改文件、调用工具和验证结果。

工具越来越强只是表层。

AI 先放大了我的效能，随后又放大了我的好奇心、创造欲、急躁和执念。它让我做得更快，也逼着我重新回答几个更难的问题：我为什么如此喜欢创造？为什么会停不下来？我真正擅长的究竟是什么？当执行越来越便宜以后，什么仍然必须由我自己完成？

回头看，我在这一年学会了使用 AI，也借助 AI 重新认识了自己。后者带来的影响更加深远。

## 一、Gemini：手拼上下文的时代

2025 年五一前后，我开始大规模使用 Gemini 2.5 Pro。

当时 Google AI Studio 给的额度很多，我不只拿它写代码，也会把工作中遇到的问题、生活里的困惑和临时产生的想法拿去讨论。它逐渐从一个偶尔使用的工具，变成了我的日常认知工具。

差不多在同一时期，我看到 Karpathy 分享过一种做法：写一个脚本，把项目相关的代码和需求一起打包给模型，让它基于完整上下文工作。

这件事对我影响很大。

那时还没有今天这么成熟的 Coding Agent。我对项目结构有一个大致认识，知道需求可能涉及哪个模块，但不会事先把里面的代码全部读一遍。拿到需求以后，我会先判断它属于哪个模块，再用自己写的脚本把相关目录和文件提取出来，和需求一起发给模型。

开始的几轮，我一般不要求它直接输出最终代码。我会先讨论：这个需求应该改哪里，可能涉及哪些模块，有哪些设计方案，不同方案的代价是什么。

模型给出建议后，我再消化一遍，把自己的判断写进下一轮提示词。等方案逐渐清楚，我会让它把需要修改的代码标出来，最后由我亲手落实到项目里。

那时还没有今天意义上的 Agentic Coding。模型不会自己在整个项目里搜索，也不会自动修改文件。上下文由我圈定，方案由我们共同形成，代码最后还是由我来改。

但正因为如此，我始终处在完整的学习闭环里。

我必须判断哪些文件和问题有关，理解修改为什么发生在这里，也必须确认生成的代码是否符合项目原来的设计。模型帮我加快了思考，却没有把我从项目里赶出去。

Git 又把试错成本降得很低。一个方向不对，我就直接回退；效果合适，再保留下来。代码不再像一件投入很多以后舍不得放弃的作品，而更像一个可以反复验证的假设。

现在回头看，手拼上下文虽然原始，却是一个很好的学习阶段。它让我理解了上下文为什么重要，也让我通过实际使用，逐渐理解 Token、prefill、decode、指令遵循、Tool Call 和 Agentic Workflow。这些东西以前我可能看过原理，甚至可以复述，但只有在模型一次次听错、跑偏和不按要求执行时，我才真正知道它们意味着什么。

很多认知都在行动中长出来。先做起来，不断遇到问题，理解才会逐渐深入。

## 二、从两天到两个小时

我一直喜欢在周末做一些自己的项目。读博时也是这样：研究暂时做不下去，我就转去做点工程上的东西。

以前受限于时间和人脑算力，一个想法从出现到真正运行起来，往往需要很久。

例如，我做过一个蚂蚁森林自动收能量的脚本。它需要先从手机截图中识别能量球，再得到坐标，最后调用手机自动化能力完成点击。截图、图像识别、坐标定位和手机操作必须串成一条完整链路。

这样的东西，以前哪怕做得快，也需要两天左右。

进入手拼上下文阶段以后，类似项目一两个小时就可以做出来。很多底层知识模型已经知道：手机自动化工具怎么连接，截图怎么获得，不同模块怎样组合。我需要做的，是理解任务、拆清结构、判断方案，并确认最终结果是否正确。

AI 同时压缩了写代码、查资料、学习陌生接口、编写样板代码以及连接不同技术模块的成本，也把“产生想法”和“看到结果”之间的距离缩短了很多。

这对我的影响非常大。

过去，一个想法值不值得做，首先要经过时间成本的筛选。需要两天的想法，我可能想想就算了。现在只需要一两个小时，很多过去不会开始的事情，都可以先做一个版本试试看。

我也在这个过程中越来越清楚地意识到：我首先是一个 Builder。

我身上“程序员”的那一部分当然重要。真正让我兴奋的，是把一个原本不存在的东西做出来。亲手写了多少行代码并没有那么重要。

我更擅长，也更喜欢做这些事情：判断一个东西值不值得做，确定方向，拆解系统，识别关键设计，验收结果，再根据反馈继续迭代。

AI 没有简单替代我的编程能力。相反，当编码成本下降以后，它把我真正喜欢的那部分工作显露了出来。

## 三、从 Opus 到 GPT-5.5：进入 Agent 时代

2025 年十月到十一月，我开始大量使用 Claude Code。Opus 4.5 的出现，也成为一个比较明显的时间点。

这一阶段的关键变化，是寻找上下文的责任开始从人转向 Agent。模型能力的提升最终改变了人机分工。

过去是我判断需求涉及哪个模块，把相关文件整理好，再交给模型。Claude Code 可以利用 Bash、命令行搜索和项目内检索，自己追踪调用关系、寻找关键文件、修改代码，并继续运行命令验证结果。

人机分工因此发生了变化：

> Gemini 阶段，我管理上下文；进入 Agent 阶段以后，我开始管理任务。

这两种方式并不能简单地说谁更好。

Agent 自动定位上下文，显著降低了使用门槛，也提高了执行效率。但手拼上下文时，我必须亲自判断模块关系，亲手应用修改，因此更容易形成对项目的细节认知。Agent 把搜索、修改甚至验证全部接走以后，人也可能慢慢退出学习闭环。

效率和学习，从来都是两套不同的指标。

到了 2026 年年初，我又深入使用过 OpenCode，也走过一些弯路。

第一类弯路是中转站。它接入方便，表面成本也有吸引力，但模型是否真实、服务是否降级、账号池是否稳定，用户都很难确认。实际体验里，同样一个模型通过中转站使用，速度和效果经常不如官方订阅。后来我基本回到了官方服务。

第二类弯路是复杂插件和巨量 Token 工作流。OpenCode 上的一些插件加入了大量角色、Agent 和流程。那段时间，为了使用这些工具，我甚至记住了不少希腊神话人物的名字。

这些复杂工作流确实可以让模型反复思考、反复执行，但消耗巨大，最后带来的收益并没有复杂度看起来那么高。

我逐渐形成了一个判断：Agent 外面的 Harness 很重要，但复杂度无法代表能力。真正决定上限的，仍然是模型，以及模型能否与搜索、修改、工具调用和验证形成稳定闭环。

后来我转向 ChatGPT 和 Codex。比较深度的分析和推演，我更多放到 GPT-5.5 Pro 上；主要的开发和执行任务，则交给 Codex。

Opus 到 GPT-5.5，仍然属于同一个 Agent 时代。这段迁移让我逐渐放下对复杂角色和工作流的迷恋，回到更强的模型、更简单的工具和更清楚的任务定义。

工具变得简单以后，人的责任反而更清晰了。

## 四、人的工作，从写代码转向前置定义

有了完整的 Coding Agent，工作方式和手拼上下文时代很不一样。

过去，我可以在写代码的过程中逐渐想清楚问题。一边修改，一边发现需求里还有哪些模糊之处，再回过头调整设计。

现在，当我把任务交给 Agent 时，很多思考必须提前完成：这个软件究竟要解决什么问题，任务边界在哪里，哪些约束不能突破，什么结果才算成功。

如果方向一开始就是错的，Agent 不会替你纠正人生。它只会以很高的效率，沿着错误方向越跑越远。

所以人的工作开始前移：

1. 定义真正的问题；
2. 把隐性的判断表达出来；
3. 给出必要的上下文和边界；
4. 设计可以执行的验收标准；
5. 判断最终结果是否真的解决问题。

自我验证闭环因此变得非常重要。

写 Web 应用时，Agent 不应该只是写完代码就宣布完成。它最好能启动应用、打开页面、执行操作、观察结果，再确认实现是否满足要求。写 CLI 时，输出最好结构化一些，让 Agent 能读取、比较和判断。

你不仅要告诉它做什么，还要告诉它什么叫“做得好”，应该用什么方法证明自己做到了。

从这个角度看，我现在做的事情越来越像管理。就像带一个执行能力很强、但对目标和责任没有内生理解的实习生：任务怎么拆、边界在哪里、结果怎么验收，都必须由管理者想清楚。

更难的一层还在后面。

管理 Agent，是决定它应该做什么。管理自己，则是回答我为什么要做这件事，它是否值得占用我的时间，以及什么时候应该停下来。

## 五、AI 是放大器，但放大器没有方向盘

在生产力突然提升以后，我一度进入过一种很像“赛博精神病”的状态。

因为自己的效率上来了，我很自然地把类似的要求放到同事身上。但很多同事并没有大规模使用 AI，也没有进入和我一样的信息密度和工作节奏。我用经过 AI 放大后的速度要求他们，对他们并不公平。

我也越来越不适应会议。

和 AI 交流时，我可以快速输入完整想法，再用很快的速度阅读回答。和人交流时，却必须等待对方以自然语言的速度输出，还要判断他的知识背景、真实意图和情绪状态。

那段时间，我会觉得和人打交道非常“耗 Token”。一句话能和 AI 说清楚的事情，和人可能要讲很久。

现在看，这种判断只看到了信息传输效率，却忽略了协作中的处境、情绪、节奏和尊严。管理需要在共同目标下建立理解和信任，人无法被优化成一个速度较慢的模型。

更明显的变化发生在生活里。

周末我总想坐在电脑前，看看还能让 Agent 做点什么。表面上在带孩子，心里却惦记着某个 Session 跑到哪一步，想找机会再改一点。去泰国旅行，我也要打开电脑，把干活的摊子支起来，甚至专门去数字游民空间工作一个下午。

Vibe Coding 很像游戏。你产生一个想法，把它交给模型，短时间内就能看到反馈。想法、执行和奖励之间的距离极短，于是人很容易不断开始下一轮。

尤其是睡觉前，绝对不能打开。一旦启动一个任务，就会忍不住想看它跑到哪里，再补一句要求，再试一个方向。最后不仅没有早点睡，脑子反而变得越来越兴奋。

我后来才意识到，AI 会放大一个完整的使用者，包括他的能力、欲望和局限。

好奇心被放大，可以成为创造力，也可以变成停不下来的冲动；高标准被放大，可以提高结果质量，也可能变成对他人的苛刻；行动力被放大，可以快速验证想法，也可能让工作不断侵入生活。

AI 可以提供巨大的动力，却不会自动提供方向。它能让我跑得更快，却不能告诉我什么时候应该停下来。

效率提升，也不会自动带来自由。如果一个人没有想清楚自己为什么做，节省出来的时间，只会被更快地填满。

## 六、回头看见那些更早的点

当我开始反思自己为什么会如此迅速地进入 AI Native 状态，很多更早的经历重新浮现出来。

### 编译器让我相信实践

大学时，我做过一个用 C 语言实现 C 语言编译器的大作业。

从词法、语法分析到生成四元式，虽然复杂，但路径还算清楚。真正困难的是从四元式生成汇编，以及后面的优化：怎么分配寄存器，怎么减少访存，怎么在有限寄存器里安排变量和中间结果。

这些东西，老师不一定会逐项讲，书上也很难直接给出适合当前实现的答案。我只能不断实验、看生成结果、修改策略，再重新测试。

后来老师请来一位英特尔的编译器专家给我们上课。那是我大学期间听过信息密度最高的一节课。专家讲得很好；更重要的是，在听课之前，我已经踩过很多坑，也积累了大量具体问题。他讲到一些点时，我会立刻知道它解决了自己过去的哪个困惑。

那次经历让我形成了一种很稳定的学习方式：先进入真实问题，通过动手暴露认知缺口，再带着问题寻找知识。

### 2025 年以前，我后悔读博；2025 年以后，我不再后悔

读博则留下了另外一些东西。

在 2025 年以前，我其实很后悔读博。那段时间过得很艰难，很多时候只能自己指导自己，也有很长时间发不出文章。与此同时，它又有巨大的机会成本。和一些同龄人相比，我错过了挣钱、积累资产和买房的窗口。粗略地说，可能相当于少买了一套房。

但到了 AI 时代，我开始重新理解那段经历。

读博留给我最重要的东西，可能是一大块可以自己调配的时间。它的价值超过了某篇论文或者那个学位。

这种时间今天看起来非常稀缺。进入工作以后，注意力经常被会议、排期、消息和别人定义好的任务切成碎片。一天看起来很忙，但真正能够沿着一个问题持续往下钻的时间并不多。读博当然也有考核、项目和毕业压力，但在相当长的一段时期里，我仍然可以决定今天读什么、研究什么、验证哪个想法，以及愿意在一个暂时没有结果的问题上投入多久。

这不仅是时间自由，更是注意力的自主权。

当时我不一定珍惜它。长时间没有产出时，这种自由甚至会变成压力：没有人告诉你正确答案，也没有稳定的反馈证明今天的投入有价值。但恰恰是在这种状态里，我学会了自己寻找问题、安排注意力，并在没有即时奖励的情况下继续做下去。

我也逐渐确认，好奇心才是支撑我长期投入一件事的动力。名声、荣誉或者领导的表扬都很难维持这么久。

这件事在 AI Native 时代非常重要。

当一个人面对大模型对话框或 Agent 窗口时，没有人天然告诉他应该输入什么。模型执行能力再强，如果人不知道自己想探索什么、想创造什么，也不会凭空得到方向。AI 可以快速完成一个定义清楚的任务，却不能替人生成内在需要。

执行越来越便宜以后，长期把注意力放在一个值得追问的问题上，自己决定把时间投向哪里，这些能力会越来越稀缺。读博给我的那段大块时间，恰好训练了它们。

所以我现在不再那么后悔读博。它的机会成本始终存在，那些损失和痛苦也都真实发生过。我也无意劝每个人都去读博士。回头看，我终于看见了那段时间另一面的价值：它让我暂时离开了一条被外部目标排满的轨道，获得了一段可以自己支配注意力、发现内驱力的时期。

我为什么愿意不断尝试新模型，为什么一个项目失败后可以直接回退再来，为什么会习惯先把第一版做出来，再通过真实反馈迭代？这些行为早在 2025 年以前就已经形成。

编译器、读博、长期独自摸索，以及那些当时看不出回报的工程折腾，早已在我身上留下了一套行为模式：相信实验，相信动手，用实践驱动认知，不害怕失败，也不把自己的判断完全建立在外部评价上。

AI 没有把我变成另一个人。它只是把执行成本突然降得很低，让这些过去形成的特质，一下子获得了巨大的杠杆。

当然，它也放大了这些特质的另一面。

这就是为什么，我不会感激苦难本身，但会感激那个在苦难里不断挣扎、行动和寻找出路的自己。

## 七、从管理 Agent，到管理自己

回头看这一年，我和 AI 的关系经历了一次很清楚的变化。

最初，我学习怎样给模型提供上下文；后来，我学习怎样给 Agent 定义任务、约束边界和设计验收；再后来，真正困难的一层落到了管理那个被 AI 放大的自己。

我现在越来越在意三个问题。

第一个问题是，我能否意识到自己正在被什么推动。

我是真的认为这件事重要，还是只是享受快速反馈？我是在解决问题，还是因为 Agent 可以继续运行，所以不断制造新的任务？我对同事不耐烦，是对方真的没有效率，还是我已经被机器的速度重新校准？

第二个问题是，我如何评价所谓的“进步”。

完成更多任务当然是进步，但它不必然意味着理解更深，也不必然意味着生活更好。Agent 可以替我搜索、修改和验证，但如果我因此失去对系统的理解，短期效率和长期能力可能并不一致。

第三个问题是，我是否有能力调整自己。

知道睡前不能打开 Agent，只是一个很小的例子。更难的是在工作、创造和家庭之间重新建立边界；接受人类沟通天然比机器慢；有意识地保留一些需要亲自理解、亲自体验的过程；不把“能自动化”误认为“应该自动化”。

这三个动作——观察自己、评价自己、调整自己——就是我现在理解的元认知。

AI 可以帮我分析外部问题，也可以像一面镜子一样，帮助我梳理自己的行为。但它不能替我完成元认知，因为需要被审视的，正是那个决定如何使用 AI 的人。

当执行越来越便宜，方向就越来越昂贵。

AI Native 的含义已经超出了把 AI 接进工作流，以及同时启动多少个 Agent。它要求重新划分人和 AI 的责任：AI 承担大量信息处理和执行，人负责定义问题、表达判断、设计验收并对结果负责；在此之上，还需要持续审视自己，确认这些结果究竟服务于什么。

## 八、Connecting the Dots

乔布斯在[斯坦福大学的演讲](https://news.stanford.edu/stories/2005/06/youve-got-find-love-jobs-says)中说：

> “You can’t connect the dots looking forward; you can only connect them looking backwards.”

人无法在向前走的时候连接这些点，只能在回头时看见它们之间的关系。

过去我把这句话理解成一种对未来的相信：那些暂时看不出意义的经历，也许有一天会发挥作用。

现在我觉得，它还有另外一层含义。

连接这些点，无需为过去发生的一切强行寻找意义，也无需感激每一段苦难。它让人借助今天获得的新视角，重新理解自己为什么会成为现在的样子：什么力量一直在推动我，哪些特质值得继续相信，哪些倾向又必须受到约束。

回头看这一年，Gemini、Opus 和 GPT-5.5 是最明显的几个时间点。它们又连接起了更多东西。

还有大学时做编译器的那个下午，读博期间长时间没有结果的自我怀疑，周末无人要求却仍然不断开始的新项目，失败后直接回退再试一次的习惯，以及后来在泰国数字游民空间里，面对几个同时运行的 Session 感到兴奋的那个我。

这些点当时并不构成一条清晰的路线。AI 到来以后，它们突然被同时照亮。

我因此跑得比过去快了很多，也第一次如此清楚地看见了自己的能力、欲望和局限。

AI 可以替我执行，可以陪我思考，也可以把我的能力放大很多倍。但它不能替我回答：我是谁，我为什么出发，我最终想走到哪里。

这也许才是我这一年最大的变化。

我学会了如何使用 AI，也借助 AI 重新认识了自己。后者会影响我更久。
